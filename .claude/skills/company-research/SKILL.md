# 혁신의숲 기업 등록 — 1차 조사

혁신의숲 기업 등록을 위한 1차 조사를 수행한다. 결과는 검수 작업대에 붙여넣을 JSON으로 출력하고 `기업등록/결과/` 폴더에 저장한다.

## 절대 원칙 (위반 시 작업 무효)

1. **실제 확인된 정보만 출력한다.** 추측·생성·조합 금지.
2. **URL은 검색 결과나 실제 페이지에서 본 것만 쓴다.** 홈페이지 주소에 제품명을 붙여 만드는 식의 조합은 절대 금지. (과거 실제 사고: `stradvision.com/svnet/`, 로고 경로를 임의 생성 → 둘 다 존재하지 않는 주소였음)
3. **확인 못 한 항목은 생략한다.** 억지로 채우지 않는다. 비어 있으면 사람이 채우지만, 가짜가 들어가면 그대로 등록되어 더 위험하다.
4. **유사 사명 주의.** 이름이 비슷한 다른 회사를 가져오지 않는다. 반드시 대표자명·사업자번호로 교차 확인한다. 확신이 없으면 비운다.
   - 실제 사례: "씨쓰리브이"(대표 강연주) vs "씨브이쓰리"(대표 양진호) — 완전히 다른 회사
   - 실제 사례: "(주)알록"이 뷰티디바이스/폐업 전자상거래/의료기기 3곳 존재
5. **출처를 말할 수 있어야 한다.** 어디서 봤는지 설명 못 하는 값은 넣지 않는다.

## 조사 절차 (기업마다 반드시 이 순서로)

### 1단계: 기업 식별
- WebSearch로 기업명 검색. 결과가 애매하면 "기업명 + 대표자명"으로 재검색.
- **대표자명이 일치하는지 반드시 확인.** 불일치하면 다른 회사다.
- 사명 표기가 다르면(예: 스트라드비전 vs 스트라드비젼) 사용자에게 알린다.

### 2단계: 홈페이지 직접 방문 (필수, 생략 금지)
- 검색 요약만 보고 끝내지 말 것. **반드시 홈페이지를 직접 열어서 확인한다.**
- 먼저 WebFetch로 시도하고, 본문이 비어 나오거나 내용이 부실하면(JS 렌더링 사이트) **브라우저 도구(mcp__Claude_Browser__navigate → get_page_text)로 실제 렌더링해서 읽는다.** 그래도 안 보이면 screenshot으로 확인한다.
- **푸터(맨 아래)와 Contact/About 하위 페이지**에서 다음을 찾는다 (연락처가 하위 페이지에만 있는 경우가 많음):
  - 사업자등록번호 (이미지로 되어 있으면 screenshot/zoom으로 읽기 시도)
  - 대표 전화번호
  - 대표 이메일
  - 로고 이미지 주소 (페이지 소스에서 실제 확인된 주소만)
- 끝까지 읽을 수 없으면 그 사실을 보고에 적고 해당 항목은 생략한다.

### 3단계: 뉴스 검색
- WebSearch로 기업명 뉴스 검색 + **회사 홈페이지의 News/보도자료 페이지도 확인**.
- 최신순 최대 5건. 기간 제한 없음. **정확도 우선** — 동명 기업 기사는 제외.
- 각 기사는 날짜/언론사/제목/URL 4개가 필요. URL은 검색 결과에서 실제 본 것만.

### 4단계: 소개글 작성
- **[참고] 소개(refIntro)**: 자유 서술. 사업 내용을 풍부하게(3~5문장). 카테고리·키워드 추출의 근거가 됨.
- **양식 소개글(intro)**: 아래 규칙 엄수.

## 기업소개글 양식 규칙

기본 문형: `☆☆기반 □□대상 ~~을 ○○하는 기업`

- 문장은 항상 **"기업"으로 끝난다.**
- ☆☆(수단/기술): AI 등 사업의 기초 기술이 있을 때만
- □□(대상): 타겟이 명시됐을 때만, 문장 앞쪽에
- ○○(액션): 제품 형태에 따라 — 앱/웹→개발·운영, 상품/하드웨어→개발·제조, 콘텐츠→제작·제공
- 서비스명은 작은따옴표: '스파인 리셋'. **서비스명이 없으면 생략한다.**
- 액션 2개 이상: 가나다순 + 마지막 앞에 '및' (예: 개발 및 제조)
- 서비스 2개 초과: 2개까지 나열 후 '등'
- **금지 표현**: 1등, 다양한, 간편, 최대, 쉽다, 전문, 누구나, 편리, 혁신, 최초, 프리미엄 등 주관적 문구
- 외래어는 한글로 (넷플릭스 O, Netflix X / 콘텐츠 O, 컨텐츠 X). 단 AI, SaaS, IoT 등 기술용어는 예외.
- **딥테크·바이오는 정확한 업계 용어를 쓴다.** (예: "모양기억 폴리머" X → "형상기억 고분자" O)
- **"플랫폼"은 웹서비스를 연상시키므로, 실제로 하드웨어/기기면 쓰지 않는다.**

## 이메일 판정 규칙

**우선순위 상**: support, info, hi, hello, contact, cs, help, ask, connect, 기업명@
**우선순위 중**: ceo, sales, marketing, ir@
**절대 금지**: tax, bill, finance, fn, account@ (세금·회계용)

**개인메일 도메인(gmail·naver·hanmail·daum·nate·kakao 등) 처리** (개인정보 법적 리스크 — 엄격 준수):
- 아이디가 **회사명·홈페이지 도메인과 일치**하거나 공용 계정명(info·contact 등)이면 → **수집하되 "검수 필요"로 표기**하고 사유를 적는다.
  - 예: 홈페이지가 `playtown.biz`인데 `playtown808@gmail.com` → 회사 공용 계정으로 인정, 검수 필요 표기
- 아이디가 회사명과 무관한 개인 이름·별칭이면 → **수집하지 않는다.**
  - 예: 홈페이지가 `physiorobo.co.kr`인데 `okpt@hanmail.net` → 개인 메일로 판단, 제외
- 이메일이 여러 개면 우선순위 높은 것 1개만.

## 서비스 수집 규칙

(한벤투 서비스 수집 로직 v2를 기업등록용으로 이식, 2026-09-04. 원본: `한벤투/서비스수집_로직.md`)

### 수집 대상
- **실제 운영 중인** 일반 사용자 대상 웹/앱 서비스: 플레이스토어 앱, 웹 서비스, 자사몰·스마트스토어, 웹 형태 모바일 URL
- 자사몰은 기업 홈페이지와 같은 도메인이어도 **포함**
- **온라인 서비스만** — 오프라인 시설·매장·프랜차이즈 자체는 수집하지 않는다
- 제외: 기업 소개용 홈페이지, 입점몰(G마켓 미니샵 등), 타사 호스팅 팬페이지(비스테이지 등), B2B 솔루션 **소개** 페이지
- B2B 판정: **"B2B라서 제외"가 아니라 "구동되는 별도 URL이 없어서 제외"**. B2B 제품이라도 별도 운영 웹/앱(관리자앱, 고객사 로그인 웹, 가맹점용 앱 등)이 있으면 수집 (사례: 리스크제로 관리자앱, LITS 빈스캐너, 글로벌텍스프리 가맹점용)

### 웹 URL 판별 — "살아있는가"가 아니라 "서비스가 구동되는 페이지인가"
- 기업 홈페이지 ✗ (bucketplace.com ✗ / ohou.se ○)
- 소개만 하고 운영되지 않는 랜딩 페이지 ✗ (baemin.com ✗, doctornow.co.kr ✗) — **앱 전용 서비스는 `webUrl`을 비운다**
- 로그인·예매·구매 등 서비스 기능이 있는 실제 구동 페이지만 ○ (kurly.com ○)
- 여러 서비스를 한꺼번에 소개하는 페이지 ✗
- 외부 도메인(스마트스토어·카페24·노션 등) 가능 — 단 링크 정상 오픈 확인
- 데스크톱 URL만 (m. 모바일 URL 금지)

### 트리아지 (기업명·홈페이지·업종으로 먼저 판단)
- **고가능성 → 심층 탐색**: 게임·콘텐츠, 플랫폼·커머스, 교육, 헬스케어 앱, 소비자 브랜드(식품·뷰티·패션·펫), 핀테크, O2O
- **저가능성 → 1회 확인 후 판단**: 제조·소재·바이오R&D·건설·설비 등 B2B. "없는 게 정상"이 기본값이지만 **반드시 1회는 검색으로 확인** (예외 사례: 볼빅몰, 리츠 빈스캐너 앱)

### 탐색 순서 (기업당)
1. **일반 검색**: `기업명 + 서비스/앱` — 사업 내용과 서비스 존재 파악
2. **공식 홈페이지**: 서비스/APP 소개 페이지, 푸터의 앱 다운로드 링크 (사업자번호로 동일 기업 교차 확인)
3. **플레이스토어**: `https://play.google.com/store/apps`에서 서비스명·기업명 검색 (브라우저 도구 사용 가능) → 앱 발견 시 **개발사 페이지를 열어 앱 전수 나열** (관리자용·원장님용 등 파생 앱 포함). **개발사명(퍼블리셔)을 반드시 확인**하고 `publisher`에 기록
   - **동명 앱 주의**: 앱 이름이 회사명과 같아도 개발사가 다르면 남의 앱. 실제 사례: MCN "플레이타운" 검색 시 메타버스 농장 게임 "플레이타운"(개발사 1zlabs)이 나온다 — 완전히 다른 회사
4. **웹↔앱 상호 확인**: 앱을 찾았으면 전용 웹 존재 확인, 웹을 찾았으면 앱 존재 확인 → **같은 서비스면 한 항목으로 통합** (`type: "웹·앱"`)
5. **자사몰**: 서비스 전용 도메인 → 홈페이지 내 몰 → `기업명 스마트스토어` 검색 순
6. **유사 사명 경계**: 동명 기업·서비스 발견 시 대표자명·사업자번호·도메인·패키지명으로 교차 확인 (예: 세이프인 3개사, Rocats≠로켓츠게임즈)
- **iOS 앱스토어 URL은 수집하지 않는다.** 플레이스토어에 없는 iOS 전용 앱이면 `type: "앱"`에 이름만 적고 `note`에 "iOS 전용, 플레이스토어 없음"

### 검증 (수집 후 전건)
1. **URL 생존 확인**: 웹 URL·스토어 URL 실제 접속. 실패 시 재탐색(패키지 변경·도메인 이전) → 찾으면 교체, 못 찾으면 제외하고 `notes`에 "종료 추정"으로 남긴다
2. **귀속(소유권) 판정**: 앱은 **스토어 등록 명의(퍼블리셔) 기준** — 개발 외주작은 해당 기업 서비스 아님. 패키지명·도메인이 기업과 일치하는지 확인 (kr.keumyoung ↔ 금영). **M&A·사업부 매각 뉴스 1회 확인** — 소유권이 넘어갔으면 제외
3. **중복 제거**: 같은 서비스의 리브랜딩·신구버전은 1건으로 통합
4. **운영 상태 의심 시그널**: 관련 기사가 수년 전뿐 + 홈페이지 접속 불가 + 스토어 미검색 → 종료 추정으로 제외

### 기록 원칙
- 실제 확인한 URL만 기재 — **URL 조합·추측 생성 금지**. 못 찾은 키는 생략
- `name`은 한글 정식명만 (괄호 영문 병기 금지). `nameEn`은 스토어 영문 타이틀·도메인·패키지명 등 **근거 있을 때만**
- `type`: `웹` / `앱` / `웹·앱`
- 확신 못 하는 건은 해당 항목 `note`에 사유를 남겨 검수자가 판단하게 한다
- **서비스 없음도 확인 결과다**: `services`를 생략하되 `servicesNote`에 업종·확인 경로를 적는다 (예: `"B2B 소재 제조 — 검색·플레이스토어·스마트스토어 확인, 서비스 없음"`) → 커버리지 확인용
- 알려진 한계 — 검색 엔진에 안 잡히는 최신·소규모 서비스는 놓칠 수 있음, 홈페이지 접속 불가(인증서 오류 등)면 탐색 깊이가 얕아짐 → 해당 시 `notes`에 명시

## 출력 형식 (JSON)

**확인된 항목만 쓴다. 빈 항목은 키 자체를 생략한다.** (생략하면 작업대가 자동으로 빈 값 처리, 빈 문자열도 쓰지 말 것)

```json
[
  {
    "name": "기업명",
    "cp": "CP00040459",
    "bizno": "000-00-00000",
    "ceo": "대표자국문명",
    "homepage": "https://...",
    "logo": "https://...",
    "phone": "02-000-0000",
    "email": "contact@...",
    "sns": ["https://linkedin.com/..."],
    "refIntro": "참고용 자유서술 3~5문장",
    "intro": "양식 소개글",
    "introEn": "영문 소개글 (intro가 있을 때만)",
    "cats": ["1순위", "2순위", "3순위"],
    "aiKws": ["키워드1", "키워드2", "키워드3", "키워드4", "키워드5"],
    "services": [
      {"name": "서비스명(한글)", "nameEn": "영문명(근거 있을 때만)", "type": "웹·앱", "webUrl": "https://...", "playUrl": "https://play.google.com/store/apps/details?id=...", "publisher": "스토어 개발사명", "note": "검수자 참고 사유"}
    ],
    "servicesNote": "서비스가 없을 때만 — 업종·확인 경로 (예: B2B 소재 제조 — 검색·플레이스토어·스마트스토어 확인, 없음)",
    "news": [{"date": "YYYY-MM-DD", "press": "언론사", "title": "제목", "url": "https://..."}],
    "notes": ["검수 포인트 — 대표자 불일치, 동명회사 제외 이력, 개인메일 수집 사유 등"]
  }
]
```

**단축 규칙**:
- **`services`**: 1항목 = 서비스 1개, 같은 서비스의 웹+앱은 한 항목(`type: "웹·앱"`). 없는 URL 키는 생략. 패키지명은 작업대가 `playUrl`의 `id=`에서 자동 추출하므로 따로 적지 않는다. 오프라인·iOS는 수집 대상 아님. 서비스가 없으면 `services`를 생략하고 `servicesNote`에 확인 경로를 적는다
- **`cp` (기업 ID)**: 사용자가 요청에 기업 ID를 같이 준 기업만 넣는다. **조사해서 알아내는 값이 아니다 — 안 주면 키를 생략한다.** 받은 형태가 `40459`든 `CP40459`든 `CP00040459`든 그대로 넣으면 작업대가 `CP+8자리`로 맞춰서 해당 기업 카드에 자동 매칭한다(뉴스 엑셀 복사의 CORP_ID 칸에도 자동으로 들어감)
- 대표자 1명이면 `"ceo": "이름"` 한 줄. 공동대표만 `"reps": [{"name":"A","sns":[]}, {"name":"B","sns":[]}]` 사용
- 뉴스는 배열만 쓰면 국내로 처리. 국외 기사가 있을 때만 `"news": {"domestic":[...], "foreign":[...]}` 형태 사용
- 정보가 거의 없는 기업은 3~4줄로 끝나도 정상 (예: `[{"name":"씨쓰리브이","bizno":"754-88-03723","ceo":"강연주"}]`)
- **`notes`**: 검수자가 봐야 할 주의사항은 채팅 보고가 아니라 이 배열에 기업별로 적는다 (검수작업대가 "⚠ 검수 포인트" 박스로 표시). 없으면 생략
- **`introEn`**: intro를 작성했으면 영문 번역도 함께 넣는다 (검수작업대의 번역 버튼은 로컬 HTML에서 작동하지 않으므로 조사 단계에서 채워야 함). 규칙: 기업명 대신 "A company"로 시작, 작은따옴표 서비스명은 공식 영문명이 확인되면 그것을, 아니면 원문 그대로 유지, 비즈니스 문체

## 마무리 절차 (반드시 순서대로)

1. JSON을 `기업등록/결과/YYYY-MM-DD_기업명.json` 파일로 저장한다 (여러 기업이면 `YYYY-MM-DD_일괄N건.json`).
2. 채팅에도 JSON 전문을 코드블록으로 출력한다 (검수 작업대에 바로 복사할 수 있게).
3. JSON 아래에 다음을 짧게 보고한다:
   - 찾지 못한 항목과 그 이유
   - 유사 사명·동명이인 등 주의사항
   - 사명 표기가 다른 경우
   - 홈페이지를 읽을 수 없었던 경우
   - "검수 필요" 표기한 항목과 사유
4. 검수는 `기업등록/검수작업대.html`을 브라우저로 열어 JSON을 붙여넣으면 된다고 안내한다.
